# Prompt Kit · 总入口

**参数：** $ARGUMENTS

## 怎么处理参数

- **为空**（或显示为字面量 `$ARGUMENTS`）：原样输出下面的菜单，然后问用户要用哪一条、用在什么对象上。不要自己替用户选。
- **一个编号**，例如 `1`：对当前对话中正在讨论的对象执行这一条。
- **多个编号**，例如 `3 6`、`1+6`：按顺序串起来执行，前一步的结论作为后一步的输入，最后给一个合并结论。
- **编号加文字**，例如 `4 把缓存换成 Redis`：把文字当作分析对象。
- **只有文字，没有编号**：从菜单里挑最合适的一条或一套组合，用一句话说明为什么选它，然后执行。

执行时：如果环境里装了对应的 `pk-*` skill，就严格按那个 skill 的完整步骤做；如果没装，就按下面的原始指令执行，指令里的每一个要求都要满足。

## 原始指令

1. 从第一性原理出发，找到最本质原因，修复一下。
2. 先问一些不清晰的问题，对齐我的喜好，然后再出 3 版方案。
3. 不要默认我提出的问题定义就是正确的。你先分析我真正想解决的底层需求，判断我有没有把症状误认为原因、把手段误认为目标。如果存在更值得解决的问题，直接指出来。
4. 不要只考虑这个改动产生的直接效果。继续推演它的二阶、三阶影响，尤其关注对其他模块、用户行为、系统复杂度和长期维护成本的潜在影响。
5. 其他领域里有没有类似的方案？用跨领域的方式全面思考，找到最优解。
6. 先假设你当前认为最合理的方案是错误的。站在最强反对者的角度，寻找能够推翻它的证据、反例和边界情况。然后重新评估方案，看看有没有更好的解法。
7. 深入分析整个代码库的 Git 历史、关键 PR 和架构演变过程。找出哪些设计是有意为之，哪些是历史遗留，哪些是为了解决已经不存在的问题而引入的。识别可以安全移除的历史包袱。
8. 假设明天有一个完全不了解项目、但是能力很强的工程师来接手。请评估他理解整个项目需要付出的认知成本，找出那些命名混乱、抽象过度、职责不清晰、需要大量上下文才能理解的代码，并提出简化方案。
9. 全面分析最近 XX 天里的所有 PR（默认 30 天），找出最慢的那几个，看看有没有导致卡顿、可以优化的地方。
10. 全面复盘最近 XX 时间（默认 30 天）的 Bug、返工、回滚和重复修改。不要只统计发生了什么，要分析这些问题背后有没有共同的根因。把能够预防的共性问题沉淀成项目规则、自动化或者 Skill，避免我们反复支付同样的成本。

## 推荐组合

- **做新功能**：`3 → 2 → 4 → 6`（问对问题 → 对齐偏好出方案 → 推演影响 → 自我推翻）
- **疑难 bug**：`1 → 6`（找根因 → 挑战这个根因判断）
- **卡在设计上**：`3 → 5 → 6`
- **接手老项目或大扫除**：`8 → 7`
- **团队效能体检**：`9 → 10`
