# 08 · 新人接手：认知成本评估

> 原始指令：假设明天有一个完全不了解项目、但是能力很强的工程师来接手。请评估他理解整个项目需要付出的认知成本，找出那些命名混乱、抽象过度、职责不清晰、需要大量上下文才能理解的代码，并提出简化方案。

**范围：** $ARGUMENTS
（如果这里为空或显示为字面量 `$ARGUMENTS`，就评估整个仓库。）

## 执行步骤

1. **模拟新人路径**：README → 安装和启动 → 入口文件 → 一条核心业务流程从头走到尾。把每一处卡住的地方，以及需要知道才能继续的隐性知识，全部记下来。
2. **扫描四类问题：**
   - **命名混乱**：同一个东西有多个名字、一个名字有多个意思、名字和行为对不上、缩写黑话
   - **过度抽象**：只有一个实现的接口、层层转发的包装、过早泛化、为了"灵活"加的配置
   - **职责不清**：上帝文件或上帝类、跨层调用、循环依赖、同一逻辑散落在多处
   - **隐性上下文**：魔法值、隐式约定（调用顺序、命名规则）、全局状态、只存在于某个人脑子里或聊天记录里的知识
3. **每个问题写清楚**：位置、为什么难懂、简化方案、收益、改动成本（小 / 中 / 大）。

## 输出格式

**认知成本评分卡**
- 跑起来需要多久
- 能独立改一个小功能需要多久
- 能放心改核心模块需要多久
- 期间至少要问人几次、问什么

**Top 10 问题清单**，按「收益 ÷ 成本」排序。

**Quick wins**：今天就能做完的，例如重命名、删掉没用的抽象、补一页架构图、在 README 补上启动步骤。

## 原则

- 用"一个聪明的陌生人"的视角，不要用"作者本人"的视角。
- 先给结论和优先级，不要罗列几百条细枝末节。
